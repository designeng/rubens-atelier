# Что взять из pi-durable

Разбор пакета [`earendil-works/pi/packages/durable`](https://github.com/earendil-works/pi/tree/main/packages/durable)
(коммит `2ce9d52` от 2026-10-29) применительно к rubens-atelier.

## Коротко

pi-durable — «durable agent harness» на TypeScript: сам ходит в модель, сам исполняет
инструменты, и всё — транскрипт, состояние, задачи — пишет атомарными коммитами в одно
хранилище (SQLite/JSONL/IndexedDB/Durable Object) до того, как что-то показать. После
падения процесса работа продолжается с последнего чекпойнта. Объём: ~30k строк исходников,
спецификация на 6400 строк (`docs/spec.md`).

У нас другой уровень абстракции: агентный цикл целиком внутри Claude Code (Agent SDK), а мы
оркестрируем *шаги* — workflow-машину над work items, Celery, Redis, Postgres. Поэтому их
движок генерации, инструменты, code mode и бэкенды хранилищ нам не нужны. Полезны идеи
уровня **задачи и прогона**: как считать падения, как классифицировать неудачи, как
моделировать владение и ожидание дочерних задач, как отдавать UI состояние, а не события.

## Что у нас уже есть (их понятие → наше)

| pi-durable | rubens-atelier | Комментарий |
|---|---|---|
| Одна линия атомарных коммитов | CAS по `work_items.version` в `Engine._enter` | У них один коммит покрывает и состояние, и постановку задачи; у нас Postgres-коммит и постановка в Redis/Celery — две записи, разрыв закрывает `reconcile` (см. идею 6). |
| `requestId` для идемпотентной отправки | Шаг и human request привязаны к версии; уникальный `Run(item_id, version)` | По сути то же. |
| Задача с чекпойнтами, переживающая рестарт | Lease + heartbeat + `reap_orphans`, `reconcile` в beat | Мы *обнаруживаем* смерть воркера, но не *продолжаем* работу (идея 1). |
| `sleeping` / `waiting` без удержания исполнителя | `check`-состояния, которые опрашивает beat; `human`-состояния | Совпадает по смыслу. |
| `afterRun`-хук «прогнать тесты после правок», fix-run при падении | `run_with_verify`: verify_command и возобновление сессии с выводом | У нас это есть и встроено; у них — как расширение. |
| `maxTurns`, `restartLimit` — защита от бесконечных циклов | `max_visits` / `on_exhausted`, `max_turns`, `max_budget_usd` | Есть, кроме счётчика рестартов. |
| `structuredOutputSchema` | Вердикт через `output_format` json_schema | Совпадает. |
| `continue` после неудачного прогона | `parent_task_id`, `resume: true` в состоянии | Есть механизм, нет политики (идея 2). |
| Лимит провайдера — не провал работы | `RATE_LIMITED`: шаг возвращается в очередь и продолжает сессию | У нас даже богаче (окна подписки, pacing). |
| Агент на беседу: модель, инструменты, cwd, instructions (примеры 26 plan-mode, 27 reviewer) | Роли из `prompts/`, `disallowed_tools`, `model`/`effort` на состояние | Совпадает. |
| `env` на беседу, скрытие секретов | Workspace на item, `agent_env()`, `secret_read_rules()`, sandbox | Совпадает. |
| `watch(from)` и переподключение | SSE с `Last-Event-ID`, архив транскриптов в Postgres | Есть; модель «события», не «состояние» (идея 5). |
| `pi.usage`: стоимость по модели и инструменту | `Run.cost_usd`, корректный расчёт для возобновлённой сессии | Есть итог, нет разбивки (идея 9). |

## Идеи, которые стоит взять

Отсортированы по соотношению пользы и затрат.

### 1. Падение воркера — неудачная попытка, а не эскалация

**Сейчас.** Если воркер умер посреди агентного шага, задача получает `failed: worker lost`,
шаг выдаёт вердикт `error`, и story уходит в `needs_human`. При этом `session_id`
сохраняется сразу при старте, то есть продолжить мы можем.

**У них.** Запрос к модели, во время которого умер процесс, считается неудачной попыткой
по `settings.retry` и повторяется после backoff. Для остальных задач действует счётчик
рестартов: каждый обрыв (crash, eviction) увеличивает его, новый закоммиченный чекпойнт
сбрасывает. Когда счётчик доходит до `restartLimit` (по умолчанию 5), задача завершается с
причиной `restart_limit` и уходит в `onReport`. Так бесконечного crash-loop не бывает, но и
одиночный OOM не будит человека.

**Что сделать.** В `steps._agent`, если прогон завершился `worker lost` и есть
`session_id`: удалить `Run` (как сейчас для rate limit), записать сессию в
`item.sessions`, увеличить счётчик `restarts` на item+version и снова отдать шаг в
планировщик. После `HARNESS_RESTART_LIMIT` (например, 3) — нынешнее поведение с причиной
`restart_limit` в артефакте. Сброс счётчика — при смене версии item. Это небольшое
изменение: нужная инфраструктура уже есть в ветке `RATE_LIMITED`.

Оговорка: у них не каждая задача безопасна для повтора (`replay: "safe"` против
`interrupted`). Для агента в git-workspace повтор через resume почти всегда безопасен: агент
видит дерево как есть. Небезопасны только наши действия с внешними эффектами (идея 4).

### 2. Типизированная причина неудачи прогона

**У них.** `docs["pi.live"].runFailure.reason` — закрытый enum: `model_error`, `no_model`,
`aborted`, `reset`, `interrupted`, `faulted`, `orphaned`, `restart_limit`, `turn_limit`,
`nothing_to_answer`, а текст отдельно в `detail`. И политика на эту причину:
`afterFailedRun: continue | withdraw`.

**Сейчас.** У нас причина — свободная строка в `error` (`describe_error`), а в workflow всё
сводится к `error → needs_human`.

**Что сделать.** Колонка `Run.failure_reason` с enum: `turn_limit` (SDK `error_max_turns`),
`budget` (`error_max_budget_usd`), `verify_failed`, `timeout`, `worker_lost`,
`restart_limit`, `rate_limited`, `cancelled`, `model_error`. Дальше два шага:

- Показывать причину на доске отдельным бейджем, а не только текстом ошибки.
- Разрешить в YAML ключи `next` по причине, например
  `next: {done: sync_base, turn_limit: implement, error: needs_human}` вместе с `max_visits`.
  Так `turn_limit` автоматически продолжает ту же сессию один-два раза («continue» без
  нового сообщения, как у них), а человек нужен только когда это не помогло.

Предостережение из их README стоит перенести и к нам: каждый `continue` начинает счётчик
ходов заново, поэтому автопродолжение обязано иметь свой предел (у нас — `max_visits`).

### 3. Steer и follow-up в работающего агента

**У них.** Вход в занятую беседу попадает во входящие (`pi.inbox`) с режимом
`whenBusy: "steer"` (вставляется после текущего раунда инструментов, агент видит сразу)
или `"followUp"` (после ответа начинается следующий прогон), а также `reject` и
`whenIdle: "reject"`.

**Сейчас.** Человек может ответить только в `human`-состоянии; `PATCH /items/{id}` во время
работы агента применяется лишь со следующего шага. Если реализатор пошёл не туда,
остаётся отменить и начать заново.

**Что сделать.** Кнопка «Сказать агенту» на работающем шаге: сообщение пишется в Redis-список
задачи. В Agent SDK стриминговый вход (`ClaudeSDKClient` или `query` с async-итератором
сообщений) позволяет дослать user-сообщение в идущую сессию. Если это окажется ненадёжным,
вариант follow-up проще: после завершения прогона, до вердикта, `run_with_verify` проверяет
входящие и, если там что-то есть, возобновляет сессию с этим текстом — тот же цикл, что и
для verify. Комментарий сохраняется артефактом `human:steer`. Прежде чем браться за steer,
надо проверить поведение SDK на прототипе.

### 4. «Effect sandwich» для действий с внешними эффектами

**У них** (spec §5.2): `закоммитить намерение → выполнить внешний эффект → закоммитить
результат`. Если процесс открылся в фазе намерения, эффект мог произойти, и обработчик
обязан либо безопасно повторить, либо опросить внешний handle, либо записать прерывание. Для
инструментов это явная декларация `replay: "safe"`.

**Сейчас.** `reconcile` перезапускает застрявшие `action`-шаги (`open_pr`, `merge`,
`sync_base`), то есть неявно считает их идемпотентными. `open_pr` устроен как «открыть или
обновить», но это свойство держится на реализации, а не на контракте.

**Что сделать.** Явно пометить действия: `ACTIONS[name] = Action(fn, replay="safe" |
"check")`. Для `merge` перед повтором спрашивать GitHub, не смерджен ли уже PR, для
`open_pr` — искать существующий PR по ветке (вероятно, уже так). Записывать
`action_started` в `ItemEvent` до вызова — тогда в истории видно, что эффект мог
случиться. Добавить тест «воркер умер после push, до advance» для каждого действия.

### 5. Отдавать доске состояние, а не поток событий

**У них.** В последней версии `watchEvents()` (`message_update`, `tool_execution_*`,
`run_end` …) удалили совсем. Причина в CHANGELOG: «рендерер рендерит состояние, а не
собирает его из событий… новая информация становится полем, а не типом события, который
должен выучить каждый клиент». UI подписывается на типизированный документ `pi.live`
(текущий прогон, стримящийся ответ, слоты инструментов, ретраи, `runFailure`) и получает
снимок плюс дельты. Длинные транскрипты отдаются окном: последние 50 записей, «загрузить
раньше» и маркеры разрывов после переподключения (`ConversationTranscript`).

**Сейчас.** Живое состояние размазано по полям хеша задачи (`activity`, `todos`, `turn`,
`rate_limited`) и по потоку событий; `web/` собирает картину из событий. Строки
обрезаются до 8000 символов, история при переподключении отдаётся целиком.

**Что сделать.** Не переписывать — двигаться постепенно:

- Ввести один типизированный «live»-объект на прогон (pydantic-модель: фаза, активность,
  todos, ход, стоимость на текущий момент, причина неудачи, verify-попытка) и отдавать его
  `GET /tasks/{id}/live` и SSE-событием `live` целиком (он маленький) при каждом изменении.
  Доска рисует шапку прогона только из него.
- Транскрипт оставить событиями, но читать окном: `?before=&limit=` уже почти есть в
  `/events?after=`, добавить обратную пагинацию и «показать раньше» в Session-панели.

### 6. Одна запись вместо двух: outbox для постановки шагов

**У них.** Всё, включая создание задачи, — в одном коммите хранилища; планировщик
вычисляется из закоммиченного состояния. Поэтому «потерянных постановок» не бывает.

**Сейчас.** `_enter` коммитит Postgres, потом отдельно вызывает `scheduler.submit` /
Celery. Падение между ними закрывается `reconcile` с задержкой `step_stale_seconds` и
Redis-ключами против дублей.

**Что сделать** (дороже, делать по боли). Таблица `outbox(item_id, version, kind)`,
запись в той же транзакции, что и переход; диспетчер в beat или отдельный цикл берёт строки
через `SELECT … FOR UPDATE SKIP LOCKED` и ставит шаги. `reconcile` тогда остаётся только
для мёртвых воркеров. Ещё дальше — перенести очередь планировщика из Redis в Postgres, но
это затрагивает квоты и лимиты слотов. Сейчас не приоритет: `reconcile` работает.

### 7. Дочерние задачи и ожидание: epic → stories

**У них** (spec §5.5, пример `23-child-tasks`): задачи и беседы образуют дерево владения.
Родитель коммитит `waiting` на список детей с политикой `allSettled` или `failFast` (первый
провал отменяет остальных) и не держит исполнителя. Отмена идёт снизу вверх: сначала
дети, потом обработчик отмены родителя. Если родитель решил исход, а дети ещё работают,
он находится в статусе `completing`.

**Сейчас.** Есть `kind` epic/story/task и `parent_id`, но эпик не умеет ждать свои
истории, и отмена эпика не каскадируется.

**Что сделать.** Новый тип состояния `wait: children` с `policy: all_settled | fail_fast` и
вердиктами `succeeded | failed`. Его, как `check`, опрашивает beat, или его будит переход
ребёнка в терминальное состояние. Плюс каскад `cancel` от эпика к незавершённым детям.
Это позволит workflow `epic.yaml`: планировщик режет эпик на истории (вердикт `split` +
артефакт со списком) → создаются дочерние items → `wait: children` → итоговый ревью.
Хорошо ложится на имеющийся `too_big`.

### 8. Хуки на инструменты как политика состояния

**У них.** `beforeTool` (заблокировать или переписать аргументы) и `afterTool` (заменить
результат) — на расширение, а расширение выбирается на беседу.

**Сейчас.** Ограничения — `disallowed_tools`, префиксы Bash и sandbox. Нельзя выразить,
например, «ревьюеру можно Bash, но не `git commit`/`git push`» или «реализатору нельзя
`git push` и `gh pr`».

**Что сделать.** В Agent SDK есть хуки `PreToolUse` / `can_use_tool`. Поле `deny_commands`
в состоянии YAML (список regex по команде Bash), которое превращается в `PreToolUse`-хук,
отвечающий агенту понятным текстом отказа. Небольшая доработка `build_options`; заодно
убирает необходимость в грубом `HARNESS_BASH_ALLOWED_COMMANDS`.

### 9. Стоимость и токены с разбивкой

`pi.usage` хранит токены и стоимость по `provider/model` и по инструменту, считая и
неудачные попытки. У нас — только `cost_usd` на прогон. Дёшево добавить в `Run` токены
(input / output / cache read / cache write из `ResultMessage.usage`) и модель; на доске
показать сумму по item и по роли. Доля кэш-попаданий сразу покажет, сколько стоит наш
`resume` против свежей сессии.

### 10. Handoff вместо бесконечного resume

**У них.** `reset(handoffNote)` начинает новый контекст с короткой заметкой; инструмент
может вернуть `control: { handoff }`, и прогон продолжается уже в новом контексте.

**У нас.** Реализатор с `resume: true` и `max_visits: 4` (плюс verify-попытки и правки после
ревью и CI) тянет одну сессию через всю историю story. Claude Code сам компактит, но
контекст копится, а стоимость каждого хода растёт.

**Что сделать.** Режим `resume: handoff`: новая сессия, в промпт которой идут план, последний
артефакт реализатора, ревью и diff против базы — всё это у нас уже есть в артефактах. Можно
включать автоматически, когда предыдущая сессия превысила N ходов или $X. Сравнить по
стоимости и качеству на нескольких stories, прежде чем делать режимом по умолчанию.

### 11. Мелочи

- **Fork сессии.** У них `fork(entryId)`. В Agent SDK есть `fork_session`. Можно попробовать
  «ревьюер стартует форком сессии планировщика»: он знает план и мотивацию, но не видит
  самооправданий реализатора. Это альтернатива нынешнему «полностью свежая сессия».
- **Таксономия отчётов.** Единый `on_report(kind, ...)` с фиксированными видами
  (`task_faulted`, `task_interrupted`, `storage_failed`, `host_error`) вместо разрозненных
  `log.exception` — основа для алертов и будущего OpenTelemetry. Их правило для телеметрии
  стоит перенять как есть: в атрибутах только ID и управляющие метаданные, никогда
  содержимое промптов и вывода.
- **Фейковые часы.** Они прокидывают `now` и `setTimer`, чтобы гонять весь harness на
  фейковом времени. У нас `utcnow()` и `asyncio.sleep` захардкожены в engine, checks и
  scheduler; инъекция часов упростит тесты таймаутов `check`, grace-периодов и pacing квот.
- **Read-only режим.** Процесс, который только показывает сессию, открывает её с
  `readOnly: true`, и любая запись отвергается. Аналог для нас — роль API-процесса без
  права трогать планировщик, если API и воркеры когда-нибудь разъедутся по правам.

## Что не берём

- **Собственный агентный цикл, инструменты (`read`/`write`/`edit`/`bash`), code mode,
  компакция.** Это работа Claude Code; дублировать её — значит потерять его
  возможности и обновления.
- **Реестр расширений и горячая перезагрузка.** Наши «расширения» — роли и YAML, они
  перечитываются и так.
- **Бэкенды хранилищ, Chord-документы, deferred commits, conformance-наборы для storage.**
  У нас Postgres + Redis, и узкого места в частоте записей нет.
- **Детерминированный replay вложенных вызовов по ключам.** Имеет смысл только когда сам
  исполняешь инструменты.

## Предлагаемый порядок

1. Идея 1 (рестарт после смерти воркера) и идея 2 (enum причин) — вместе, это одна
   доработка `steps._agent` и `Run`.
2. Идея 4 (контракт повтора для действий) — тесты на падение между эффектом и `advance`.
3. Идея 8 (`deny_commands` через `PreToolUse`) и идея 9 (токены).
4. Идея 3 (follow-up и steer) — сначала прототип SDK.
5. Идея 7 (epic с `wait: children`) — когда понадобятся эпики.
6. Идеи 5, 6, 10 — по мере того как упрёмся в UI, надёжность постановки и стоимость.
