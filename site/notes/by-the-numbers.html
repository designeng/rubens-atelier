35 merged PRs, $0.66 each: rubens-atelier by the numbers

Denis Savenok · November 2026

In the first note I wrote about what it took to make coding agents dependable. People asked the follow-up questions: how does it actually work, and what does it cost? Here are the answers, with real numbers.

Over two weeks (Oct 29 to Nov 13) the factory ran 159 agent steps and got 35 stories merged. 28 of those 35 were features of rubens-atelier itself: the dependency system between tasks, budgets, the sandbox health check, the prompt-injection guard. The factory was building itself.

$0.66median cost of a merged story
~28 minmedian time from start to a PR ready for review
77%approved by the AI reviewer on the first pass
$53total spend for all 159 agent runs
9 of 35hit a merge conflict and the agent fixed it
3 of 35needed a human before the final merge

Where the money goes

The implementer costs about 70% of the total ($36.76). The planner costs $10.24 and the reviewer $6.01, about 12 cents per review. Costs vary a lot: the cheapest story cost $0.22 and the most expensive $10.05, so the average ($1.30) is twice the median. A handful of large tasks drive the bill, which is why each story and project can have a hard budget.

About 89% of the input tokens are cache reads. Every request re-reads the whole session, so prompt caching is the difference between "cheap" and "unaffordable". It is also why a long session gets replaced by a fresh one that starts from short summaries.

The state lives in a database, not in the model

Each workflow is a small state machine written in YAML. Stories, transitions, runs and the hand-offs between agents are stored in Postgres. Queues, live event streams and short-lived locks are kept in Redis. The agent never picks the next state. It returns a verdict from a fixed list, and the workflow maps that verdict to the next step.

Workers crash. The factory notices.

A worker that takes a task holds a lease that expires after 30 seconds and renews it every 10. If the worker dies, the lease runs out, a reaper marks the run as lost, and the step is sent again. The agent then resumes its own session instead of starting over.

Doing the same thing twice is harmless

Every story has a version number that goes up on each transition. A step carries the version it was created for, so a duplicated or late message can't move the story. On top of that, the database allows only one run per story version.

Agents pass notes, not transcripts

Each step leaves an artifact: the plan, the implementer's summary, the review, the CI log, a human's comment. The next agent gets the latest version of each. A resumed session receives only what is new since its last visit.

Parallel work, on two levels

In Git, every branch merges the latest main before review, and conflicts go back to the implementer. That happened in 9 of the 35 stories. At the planning level, a story can be blocked by other stories (cycles are rejected). It starts by itself once they are merged.

How quality is measured, honestly

There is no benchmark suite yet. The signals I track are the reviewer's verdicts (40 approvals, 12 requests for changes), how often a story is sent back, how often it needs a human, and failed tool calls per run. Every PR was still reviewed and merged by me. The 77% figure tells you how often the AI reviewer is satisfied, not how often the code is perfect.

Caveats: a small sample, picked by me, on my own repositories, mostly on Claude Sonnet. Most of these repos had no CI configured yet, so CI rarely had anything to check. Token-level figures cover the 32 most recent runs, recorded after token tracking was added.

What's next

A proper evaluation set of issues with known-good outcomes, so changes to prompts and models can be compared on something better than a feeling.
